# End-to-end audit: security, privacy, user experience (2026-10-29)

Audited at `8e12646` (branch main), live site zceipt.xyz as served that day (every file under
`/verify/` and the landing page matched the repo byte for byte; the wasm hash matched). Nothing
was committed, pushed or changed; this report is the only addition. Method: one full pass by hand
over the web surfaces, the snap, the CSP and live headers, then the live site walked as a
first-time user (verifier samples, demo signing, the make page end to end on testnet with the
public demo wallet, docs, phone width), then five parallel deep dives (browser and JS injection;
Rust changes since the hostile audit; the API server; privacy of the make and verify flows; the
CLI and docs as a new user). Every deep-dive finding quoted here was re-checked against the code.
The three prior audits (`AUDIT-HOSTILE.md`, `AUDIT-RERUN.md`, `AUDIT-PRIVACY.md`) were read first;
their fixes were verified and are not repeated.

## Bottom line

- **No forgery.** No way was found to make a receipt accepted for a payment the presenter's key
  did not authorize, in Orchard, Ironwood or the new Sapling path. The hostile audit's HIGH fixes
  (H-1 flag routing, H-2 trailing bytes, H-3 unpinned policy, M-1 delegation) are real.
- **One HIGH in security:** the new Sapling receipt kind (`zip311z1`) regresses H-1. `zceipt verify`
  ignores `--challenge`, `--min`, `--memo-contains`, `--expect-address` and every other check flag
  on a Sapling receipt and prints VERIFIED, exit 0 (reproduced on the real testnet receipt).
- **One HIGH in privacy:** `zceipt create --seed-stdin|--ufvk --height H` ends the wallet scan at
  `H-1`, so the chain server learns the payment's exact block, which the README says was fixed.
- **CI on `main` is red** (last four runs): the pinned toolchain has no `rustfmt`, so the `rust`
  job dies at `cargo fmt --check` and never runs the tests. Locally, one core test fails at HEAD
  (`binary_magics_are_distinct`: Sapling reuses the `ZRCT` magic) and stops the suite under fail-fast.
- **The browser verifier fails open on finality** when the tip height is unknown, and the batch
  path skips the one-payment-one-request check.
- **UX:** the product works, and the make page proved a real testnet payment end to end in under
  a minute. The pitfalls are at the first step (what is a birthday, where is my viewing key, how
  long will this take, which network), in CLI error paths, and in docs that assume a checkout.
  Every docs page's GitHub link is a 404.

Suggested order: S-1, S-2, P-1, then S-3/S-4 together, then P-2/P-4 (the make page's disclosure
and review step), then U-1/U-2/U-3. Each is under a day.

## User experience

Measured on the live site: the public demo wallet's payment appeared within seconds of "Open
wallet" (its birthday is 123 blocks before the payment), the proof took about 30 s, and clicking a
payment while the scan was still running ended the scan at the window boundary as designed. The
testnet scan ran at roughly 50 to 100 blocks per second in this browser.
